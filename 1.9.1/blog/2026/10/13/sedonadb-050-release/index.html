    SedonaDB 0.5.0 Release¶

    The Apache Sedona community is excited to announce the release of SedonaDB version 0.5.0!

    SedonaDB is the first open-source, single-node analytical database engine that treats spatial data as a first-class citizen. It is developed as a subproject of Apache Sedona. This post also highlights several changes from SedonaDB 0.4.1, which did not receive a separate release post.

    Apache Sedona powers large-scale geospatial processing on distributed engines like Spark (SedonaSpark), Flink (SedonaFlink), and Snowflake (SedonaSnow). SedonaDB extends the Sedona ecosystem with a single-node engine optimized for small-to-medium data analytics, delivering simplicity and speed for spatial data that distributed systems and general-purpose databases cannot.

    Release Highlights¶

    The SedonaDB 0.5.0 release features a number of exciting updates!

    • FileFormat reorganization
    • Python support for DataFrame.unnest()
    • Improved raster functionality
    • GeoPandas-compatible API coverage
    • Improved spatial function coverage
    • Extensible table providers

    As usual, Python users can install from PyPI:

    # pip install --upgrade "apache-sedona[db]"
import sedona.db

sd = sedona.db.connect()
sd.options.interactive = True
f = sd.funcs

    R users can install from R-multiverse:

    install.packages(
  "sdplyr",
  repos = c("https://community.r-multiverse.org", "https://cloud.r-project.org")
)

    We'll use a few example datasets from geoarrow.org's data section:

    cities_url = "https://raw.githubusercontent.com/geoarrow/geoarrow-data/v0.2.0/natural-earth/files/natural-earth_cities.parquet"
countries_url = "https://raw.githubusercontent.com/geoarrow/geoarrow-data/v0.2.0/natural-earth/files/natural-earth_countries.parquet"

    FileFormat reorganization¶

    Previous versions of SedonaDB could read popular spatial file formats such as FlatGeobuf, Shapefile, and GeoPackage in addition to GeoParquet and Parquet. However, SQL, Python, and R used slightly different code paths, and formats such as CSV and JSON were supported in SQL but not in Python or R. In 0.5.0, all reads go through the same pathway for better consistency among bindings. For example, all of the following access the same dataset through the unified format machinery:

    sd.read(cities_url)
sd.read(cities_url, format="parquet")
sd.read.parquet(cities_url)
sd.sql(f"SELECT * FROM '{cities_url}'")

sd.sql(f"CREATE EXTERNAL TABLE cities STORED AS PARQUET LOCATION '{cities_url}'")
sd.sql("SELECT * FROM cities")

    Python support for DataFrame.unnest()¶

    One of my favorite functions in R has always been tidyr's unnest_longer(), which in SQL is an UNNEST and in Python has a few names depending on which DataFrame API you're dealing with. SedonaDB's version is unnest(), which works nicely with ST_Dump() to separate multigeometries and geometry collections into one row per component geometry.

    countries = sd.read.parquet(countries_url)

country_parts = (
    countries.mutate(parts=countries.geometry.geo.dump())
    .select("name", "continent", "parts")
    .unnest("parts")
    .select("name", "continent", geometry=sd.col("parts")["geom"])
    .rename(country="name")
)

(
    country_parts.group_by("continent")
    .agg(parts=f.count(sd.col("geometry")))
    .sort(sd.col("parts").desc())
)

    Improved raster functionality¶

    In our last release post we warned that we're not quite ready to announce raster support in SedonaDB. In 0.5.0, we're still not quite ready to make a splash; however, we've made substantial progress in the underlying plumbing so that one can now solve a few real-world problems. For example, you can now pass a NumPy array with bounds into a SedonaDB Raster query without copying any pixel data (in this case, using RS_Value() to sample it with an existing geometry column).

    import numpy as np
from sedonadb.raster import Raster

pixels = np.arange(256 * 256, dtype="float32").reshape(256, 256)
raster = Raster.from_numpy(
    pixels,
    bbox=[-180, -90, 180, 90],
    crs="OGC:CRS84",
)

t = sd.read(cities_url)
t.mutate(raster_value=f.rst.value(raster, t.geometry)).sort("name").limit(5)

    We've also implemented raster/vector joins à la Sedona Spark so that interactions between rasters, N-D arrays, and vector features can be expressed in a SedonaDB logical plan. For example, calculating the mean annual number of dry days across raster cells in each country can now be expressed with:

    # pip install sedonadb-zarr
import sedonadb_zarr

sd.register(sedonadb_zarr.ZarrExtension())
era5_url = "https://weathermapdata.rdrn.me/era5_2015_2020_l5.zarr/2"
era5 = sd.read(era5_url, format="zarr", options={"arrays": ["rain_ok"]}).alias("era5")
countries = countries.alias("countries")

country_chunk_stats = era5.join(
    countries,
    on=f.rs_intersects(era5.raster, countries.geometry),
).select(
    country=countries.name,
    stats=(era5.raster.rst.slice("year", 0).rst.zonal_stats_all(countries.geometry)),
)

country_totals = (
    country_chunk_stats.group_by("country")
    .agg(
        dry_day_sum=f.sum(sd.col("stats")["sum"]),
        pixel_years=f.sum(sd.col("stats")["count"]),
    )
    .filter(sd.col("pixel_years") > 0)
)

(
    country_totals.mutate(
        mean_dry_days=(country_totals.dry_day_sum / country_totals.pixel_years)
    ).sort(sd.col("mean_dry_days").desc())
)

    GeoPandas-compatible API coverage¶

    Over the past few releases, our fearless leader and PMC chair, Jia Yu, has been working toward a GeoPandas-compatible API to help GeoPandas users get started with SedonaDB. The compatibility layer is still experimental but supports a number of common GeoPandas operations.

    # pip install sedonadb-geopandas
import sedonadb_geopandas as sgpd

countries = sgpd.GeoDataFrame(sd.read(countries_url)).to_crs("EPSG:6933")
countries = countries[["continent", "geometry"]]
countries["geometry"] = countries.geometry.buffer(100_000)
(countries.dissolve(by="continent").to_crs("EPSG:4326").to_geopandas())

    Unlike GeoPandas, a sedonadb_geopandas.GeoDataFrame remains lazy and is materialized when required (e.g., on .to_geopandas()). This allows SedonaDB's optimizer to do its magic and transparently parallelize the computation; however, it does mean that row order is not guaranteed and operations that need that assumption are not supported.

    In addition to providing a familiar interface for users, GeoPandas compatibility lets us run GeoPandas tests, which has helped us catch a number of bugs in the underlying implementation.

    Improved spatial function coverage¶

    Since the 0.4.0 release, we have been fortunate to work with contributors to add 39 new ST_ and RS_ functions to our growing catalog. These include rs_asgeotiff, rs_asraster, rs_bandisnodata, rs_clip, rs_fromgdalraster, rs_geotransform, rs_makeemptyraster, rs_minconvexhull, rs_polygonize, rs_replacebandnodatavalue, rs_reprojectmatch, rs_resample, rs_setbandnodatavalue, rs_setgeoreference, rs_setvalue, rs_stack, rs_summarystats, rs_summarystatsall, rs_tile, rs_value, rs_values, rs_zonalstats, rs_zonalstatsall, st_buildarea, st_convexhull_agg, st_delaunaytriangles, st_exteriorring, st_geohash, st_geomcollfromtext, st_hausdorffdistance, st_linefromtext, st_linestringfromwkb, st_makeenvelope, st_mlinefromtext, st_mpointfromtext, st_mpolyfromtext, st_pointfromtext, st_pointfromwkb, and st_polygonfromtext. This brings the SQL reference to 210 ST_, RS_, and S2_ function pages, which are tested against PostGIS, SedonaSpark, and/or BigQuery for compatibility wherever possible. Check them out in our continuously improving SQL reference documentation!

    Extensible table providers¶

    Over the last few releases, we've been working on our extensibility layer so that less commonly used features can live in separate Python or R packages and contributors can maintain features in dedicated workspaces. The latest additions provide the machinery required to implement table providers, scans, and asynchronous streams across library boundaries. This work lays the foundation for integrations such as Apache Iceberg and custom catalog hierarchies.

    What's Next?¶

    As always, we're busy fixing bugs and working on new features for the next release. Stay tuned for new readers, improvements to existing readers, improvements to raster performance and syntax, and foreign catalog support.
